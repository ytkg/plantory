# 接続安定性の調査記録

Issue #78 の実装時点の記録です。実機の連続稼働結果は、ここに追記するまで未検証として扱います。

## 確認できた実装上の要因

- 以前は映像・音声とも1接続の終了を待ってから次の接続を受け付けていた。そのため、切断を検知できない接続は以後の閲覧開始を待たせた。
- 映像はネットワーク送信中にもカメラmutexとカメラフレームを保持していた。遅い接続が5MP撮影や他の映像取得を待たせる構造だった。
- Wi-Fi接続は起動時だけ明示的に試行し、切断後のmDNS再初期化と復帰記録を行っていなかった。

これらは報告された「時間が経つと開けない」症状の原因候補であり、実機で再現していないため単独の原因とは断定しません。

## 実装した対策

- 映像・音声それぞれで最大3接続を管理し、同一ページの映像・音声は同じ閲覧枠として扱う。4人目はHTTP 429を受け、ページ側で接続上限を表示する。
- カメラフレームを最大192 KiBの共有PSRAMバッファへコピーして返却してから、各接続へ送る。送信待ちでカメラmutexを保持しない。
- 各送信の上限を1秒とし、遅い・切断済みの接続は停止して枠を解放する。
- Wi-Fi切断を検知するとmDNSを停止し、5秒間隔で再接続する。復帰時にmDNSとOTAを再開する。
- ブラウザは映像を常に再接続し、利用者が再生を開始した音声だけを再接続する。音声がブラウザの自動再生制限で再開できない場合は再生操作が必要である。

## 実機検証（未実施）

このリポジトリの実行環境にはGit管理外の`include/secrets.h`がないため、Wi-Fi設定を含むビルドと実機書き込みは実施していません。次の結果を、使用したfirmwareのコミット、端末・ブラウザ、ネットワーク、開始・終了時刻とともに記録します。

1. 3台で映像・音声を24時間連続再生する。
2. 途中で各端末を切断・再接続し、残りの閲覧が継続し、新しい閲覧が開始できることを確認する。
3. 4台目で上限表示になり、既存3台が継続することを確認する。
4. Wi-Fiを一時切断して復帰させ、IP直打ちと`.local`を別々に確認する。開いているページの映像、利用中の音声が再接続することを確認する。
5. 3台の閲覧中に5MP撮影を行い、静止画取得後にすべてのライブ映像が再開することを確認する。

共有バッファの上限超過、送信タイムアウト、Wi-Fi切断・復帰はシリアルログに記録されます。異常時は稼働時間、空きPSRAM、接続数、Wi-Fi状態と合わせて採取します。
